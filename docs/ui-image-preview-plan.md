## 1. 问题

V1 的列表里，**图片大于 512 KiB 就没有缩略图**。这不是"可以更好"，是"现在就是坏的"：
行内只剩一个占位图标，用户必须点开预览才能知道那张图是什么。

而"悬停图片"（hover 时浮出一张更大的图）是另一件事 —— 它需要像素，而像素要么来自原图、
要么来自服务端转码。本文把两者分开评估，因为它们的代价与收益完全不同。

## 2. 现状（代码事实，逐条有出处）

| 事实 | 位置 |
|---|---|
| 缩略图三档：无数据 → 占位；`size > 512 KiB` → **占位图标，不加载任何图**；否则 `<img src=…/data>` | `public/ui_v1/js/components/row-content.js` 的 `buildThumb` + `THUMB_MAX_BYTES = 512 * 1024` |
| 大图占位带的说明是「图片较大（…），点击预览查看」；无数据是「服务器上没有这条记录的图片数据」 | 同上（`thumbPlaceholder` 的 `title`） |
| 缩略图 30×30、`object-fit: cover`、`loading="lazy"` | `public/ui_v1/css/components.css` 的 `.cell-content__thumb` |
| 数据端点 = **R2 纯透传**：无缩放/转码，`cache-control: private, max-age=60`，支持 Range | `src/ui/routes.ts` 的 `GET /ui/api/history/:type/:hash/data` |
| 预览对话框加载**原图**（`max-height: 64vh`）；只有文本 `textTruncated` 时才先取全文 | `public/ui_v1/js/components/preview.js`、`.dialog__image` |
| 悬停浮层**只挂在行内正文**上；图片行悬停出来的是**文件名**，不是图 | `list.js` 的 `tooltip.attach(textEl, …)` + `format.js` 的 `previewText` |
| CSP：`img-src 'self' data:` ⇒ 同源端点与 `data:` 可用，**`blob:` 不在白名单** | `public/_headers` 的 `/*` 段 |
| 上传体量上限 `48 MiB`（ceiling 64 MiB）；上游客户端 `MaxFileByte` **默认 20 MB** | `src/requestLimits.ts` |
| 新增一个 `/ui/api/*` 端点 = 清单 18 → 19，三处要同步 | `test/ui-guard.test.ts` 的 `EXPECTED_API_ROUTES`、`docs/ui.md` §5、`AGENTS.md` §1 表 |
| `/ui/api/*` 中间件默认给 `no-store`；端点可自带 `cache-control` 落在例外里 | `src/ui/routes.ts` 的中间件注释 |

一整张 32 MiB 的下载，`loading="lazy"` 只推迟它不减少它"，属于**判断**，不是量出来的分位数。

## 4. 平台能力（官方文档 + 实测）

### 4.1 结论：**这个 zone 的 URL 形态不可用，Binding 形态可用**

| 形态 | 结果 |
|---|---|
| `/cdn-cgi/image/width=64/<公开资源>` | **404（Cloudflare 页）** ⇒ 该 zone 没有启用 Image Resizing 的 URL 形态；且它连我们**带鉴权**的数据端点也拉不动（它自己去 fetch 那个 URL，没有我们的会话） |
| `env.IMAGES`（`[images] binding = "IMAGES"`） | **可用**：吃**原始字节**（R2 流即可）⇒ 私有数据没有"必须公开"的问题 |

### 4.2 Binding 的能力与代价（Cloudflare 文档）

- 输入上限 **20 MB**、边长 ≤ 12,000px（WebP/AVIF 有单独口径）；输入格式含 PNG/JPEG/GIF/WebP/SVG/**HEIC**；
  输出 PNG/JPEG/GIF/WebP/AVIF，且 `.output({ format })` **必填**。
- 计费按**每月唯一变换数**：Free 档 **5,000 次/月免费**，超出 $0.50/1,000（超出不扣费、只对新变换报错）。
  「唯一」= 源图 × 参数，**同一个月内重复请求只计一次**。
- **绑定响应不会自动缓存**（文档明确建议自己设 `Cache-Control` 或开 Workers Cache）。
- 本地 `wrangler dev` 支持（**低保真子集**：`width`/`height`/`rotate`/`format`）⇒ 端点可被本地套件与探针覆盖。

### 4.3 实测（本地 `wrangler dev` + 真实 Cloudflare 边缘，源图 = §3 那张 994 KiB PNG）

| 输出宽度 | 真实边缘输出 | 边缘变换耗时（`x-resize-ms`） |
|---|---|---|
| 64px | 5,782 B | 118 ms |
| 160px | 17,886 B | 167 ms |
| 320px | 42,014 B | 279 ms |
| 640px | 101,948 B | 407 ms |
| 1024px | 193,546 B | 575 ms |

- 本地同图（低保真实现，输出体积与线上不同）：64px 1,750 B / 79 ms；160px 6,082 B / 67 ms；320px 15,150 B / 95 ms。
- **同参数重复请求不复用**：边缘 295/231/223 ms、本地 408/415/378 ms ⇒ 每次都要重编码
  ⇒ 端点必须自带长缓存（源是内容寻址的 hash ⇒ 变体可以 `immutable`）。
- 合成 19.34 MiB 图（本地）：320px → 2,328 B / 660 ms（首帧）。
- 合成 22.0 MiB 图（本地）：**本地实现没有执行 20 MB 上限**（200 + 1,252 B）⇒ 上限只在线上生效，
  端点也必须自己加体积门，不能指望绑定报错。
- 生产取图 A/B（994 KiB）：**走沙箱代理更快**（中位 0.72 s vs 不走 1.39 s）⇒ 引用数字一律取快的口径。

## 5. 设计树与待拍板的四个选择

```
D1 要解决什么？ ──┬─> D3 变体从哪来？ ──> D4 归属/时机 ──> D2 悬停形态（受 D25 约束）
                  │   服务端 binding / 客户端 canvas / 不变体
                  └────────────> D5–D7 缓存口径 · 边界 · 登记与验证（尚未展开）
```

**D1 · 目的**（推荐：优先"列表缩略图覆盖全部图"）
- (a) 列表里 >512 KiB 的图根本没有缩略图 ← **真实痛点**（§3：1/1 张图踩这里）
- (b) 悬停不点开就多看一点 ← 点击预览本来只有一步，单独看价值最低
- (c) HEIC 等浏览器不认的格式在列表里显示不出 ← 纯功能收益（binding 能转码）
- (d) 维持现状

**D2 · 悬停形态**（推荐：**只放大已加载的缩略图，约 160px；不做 320px 级大浮层**）
- 图片浮层与文本浮层不同：一遮就是一片，且必须继续遵守 §3.3 #26 的 D25 决定
  （`pointer-events: none`、不挡下面几行、无内部滚动/交互）。
- 真正看清图仍是"点击 → 预览对话框"（那条路已经加载原图）。

**D3 · 变体从哪来**（推荐：**服务端 binding**）
- (a) 服务端 binding + 新端点（如 `GET /ui/api/history/:type/:hash/thumb?w=320`）：实测可行、账号接受、
  免费额度 5,000 唯一变换/月；代价见 §7。
- (b) 客户端 canvas 降采样：零基础设施、零额度，但**必须先把原图整份下下来**（994 KiB 或 32 MiB）
  ⇒ 省不了带宽（本需求的目标正相反），且 CSP 要加 `blob:`。
- (c) 不变体：只放大 ≤512 KiB 那档已加载的缩略图，大图永久保持占位。

**D4 · 归属与请求时机**（推荐：**(a) 先落地，再看要不要 (c)**）
- (a) **列表渲染时就取小变体当缩略图** ⇒ 悬停只是放大它，**零额外请求**，每图每月固定 1 次计费；
- (b) 只在悬停时按需取 ⇒ 列表保持现状，且未命中缓存时每次悬停要等 100–600 ms 才出图；
- (c) 两个尺寸都要（列表 40px + 悬停 160px）⇒ 每图每月 2 次变换，仍远在额度内。

> **对"是否需要新增 API"的正面回答**：**需要，但它不是给 hover 专用的** —— 它的主用途是让
> **列表缩略图**覆盖到全部图片（D1-a）；hover 只是它顺带的第二个尺寸（D4-c）。

## 8. 边界与风险（已知，未解决）

- **>20 MB 的源**：我们**收 48 MiB**，绑定只吃 20 MB ⇒ 这一档只能回退占位（上游客户端默认
  20 MB，所以这一档在真实使用里少，但不是不存在）。
- **HEIC**：binding 支持输入，但"浏览器认不认输出"要等真机验；这条是 (c) 的收益来源，**未实测**。
- **SVG**：Cloudflare 文档明说不缩放 SVG（会忽略参数）—— 若源是 SVG，这条端点等于白跑一次。
- **不复用缓存**：每次请求都重编码 ⇒ 缓存只能靠我们自己的 `Cache-Control`（源内容寻址，可 `immutable`），
  若改成 `private, max-age=60`（照抄数据端点）就会每 60 秒重编码一次。
- **请求量**：若 D4 选 (a)/(c)，一页 50 行全是图就会一次打 50 个端点请求（浏览器并发受限）；
  若选 (b)，鼠标扫过一列就是每个停够 150 ms 的行各打一次 —— 两种都要在设计时算一遍。
- **`hasData=false`**：这类记录（线上真实存在）必须继续走占位，不能变成 404 循环。
