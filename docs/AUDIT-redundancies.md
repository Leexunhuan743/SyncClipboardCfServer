## 1. 总体结论

**这个项目的工程质量高于它自己的"测试开发版"定位。** `src/` 里每一处"看起来奇怪"的写法，
绝大多数都能在 `protocol.md` 的差异表或 `design.md` 的 ADR 里找到**明确的、有实测支撑的**决策记录。
真正属于"无价值残留"的死代码总量**远小于**项目体量。

五条结论（本次重写后仍然成立）：

1. **可安全删除的死代码是"零散的"，不是"成片的"**：13 条里 10 条为 Low（未引用的导出、未调用的方法、
   无生产者的 CSS 规则、不可达分支），合计约 200~300 行。其中 **D-05 与 D-08 不是冗余而是缺陷**
   （注释与事实相反 / 一个真实的功能缺口），**不应与纯删除项混在一起执行**。
2. **最大的"冗余体积"是双前端并立，但这不是可以单方面清理的对象**：两版各有对方缺失的修复。
   **定位已定** —— `ui_v1` 是产品/默认界面，`ui_v2` 是允许破坏性重构的开发版。
   既有审计文档把它判为"直接删除 V2"是**过度结论**；它顺带主张删的三个服务端端点更是**事实错误**
   （那三个端点产品面也在调，删掉会打断默认界面，并撞 `ui-guard` 的路由盘点断言）。
3. **收益最高的技术改动不是删除，而是修两处具体缺陷**：`/ui/api/overview` 每次请求重复执行
   同一批查询（含 R2 全桶扫描）；以及开发版回退了产品面已修的缺陷。
4. **"重复实现"最集中的地方是测试套件，不是产品代码**：内存 D1 替身 4~5 份、multipart 构造器 5 份、
   递归 walker 3 份、`stripComments` 3 份；还有一处**高危** —— 一份测试逐行复刻了会话密钥派生管线
   用于伪造会话（**已收敛**，见 T-01 的现状）。
5. **「对齐上游」的投入是真的**：`src/` 里所有"为对齐上游而多出来"的实现都逐条落到了上游 C# 源码上
   （三种 SignalR 传输、批量 500、File→Image 提升、5 个从不写入的镜像列、统计口径、软删广播 /
   硬删不广播、工作目录命名、`/api/version` 取值）—— **逐条对上** ⇒ 这些**不是包袱**。
   尤其**不要清**：`src/pathCase.ts`、SSE / 长轮询、`tools/ab-upstream-probe.ps1`、限速系统。

**一项有用的反向事实**：官方客户端实际只调用 `/api/version`、`SyncClipboard.json`、`/file/*`、
`PROPFIND`、`/api/history*`（query / 单条 / data / PATCH / POST）这一小片端点面 ——
**`/api/history/statistics` 与 `/api/history/clear` 客户端都不用**（后者只有本站界面用），
且 `PROPFIND` 的响应体在默认配置下**从不被解析**（只判状态码）。这既解释了若干"看起来多余"的实现
为何无害，也意味着改动这些端点**不必担心打断客户端**。

### 1.1 两条排序刻意不同，不要混读

- **收益排序**（做什么最值）：修 O-01 / 补产品面缺口 → 抽共享实现 → 删零散死代码 → 双前端收尾。

## 3. 对"上一份同名审计文档"的勘误（仍有用）

本仓库在本次审计前存在一份同名文档（353 行），**从未被 git 跟踪**，因而是**就地覆盖**的，
其原文已不可从 git 历史找回。它的**行数断言全部准确**，但**行号断言错误率很高**，
而且有两条**照抄会出事**的结论。这一节保留下来，因为它是"审计文档自身也会错"的最好样本：

| # | 旧断言 | 核对结果 |
|---|---|---|
| **最危险的一条** | `schema.sql:8-10, 16-18` 是「死列」 | ❌ **实质错误**：那几行是 `Size` / `TransferDataFile` / `LastModified` / `Stared` / `Pinned` —— **全部是被读写的活跃列**。真正的死列是 `TransferDataSha256` / `TransferDataMd5` / `"From"` / `Tags` / `ExtraData`。照抄会导致**功能损坏** |
| **第二危险的一条** | 删 `ui_v2` 时应一并删 `/ui/api/overview`、`/activity`、`/history/batch-meta` | ❌ **事实错误**：三者**都被产品面真实调用**；删除会打断默认界面并撞 `ui-guard` 的路由盘点断言 |
| 第三条 | `tools/ab-upstream-probe.ps1`「完成历史使命，建议归档或移除」 | ❌ 与文档冲突：它是 ADR D10 正式登记的**真上游 A/B 守卫**，也是 `protocol.md` §10 多条"有意偏离"的唯一实测依据。**不应按死工具处理** |
| 其余 | `src/db.ts` 的"6 个死列相关"行、`src/ui/routes.ts` 端点行号、`totalHistorySize` 的调用点、`src/env.ts` 的行号等 | ❌ 错误集中在**跨几十行的错位**，不是 ±1 漂移 |
| 行数类 | `src/pathCase.ts` 86 行、`test/fixes.test.ts` 1085 行等 | ✅ 准确 |

**结论**：本文件取代旧文档成为审计结论的唯一出处。**教训**：审计结论里的行号会随改动漂移，
而"哪些是活跃列""哪些端点在用"这类**语义判断**才是真正要复核的东西 —— 行号错了最多指错位置，
语义判错会直接改坏代码。

## 5. 兼容层与适配代码（C-01 ~ C-09）

分三类，**处置方式完全不同**：

**5.A 真·遗留适配（可清理）** —— C-01（V2 的页面壳）、C-02（V2 `filters.js` 的一处默认值）：
都属开发版内部的小壳子，**删它不如等重写**（C-02 另需先确认语义）。

**5.B 上游契约型兼容（需产品决策，不是清理对象）** —— C-03（`pathCase.ts` 的路径大小写归一）、
C-04（SSE / 长轮询）、C-05（协议面不转义 `LIKE` 通配符）、C-06（hash 等值匹配 vs 上游 LIKE 模式）、
C-07（弱凭据双模式）、C-08（`schema.sql` 的清洗 `DELETE`）、C-09（5 个从不写入的镜像列）：
前六条**都是"对上游逐字对齐"的投入**，放弃它们会变成"有意偏离"，需同步改 `protocol.md` §10 与多条测试。
**唯一可放心删的是 C-09**（上游同样从不写入、DTO 也不暴露）。

**5.C 运行环境型适配（应保留，不要清理）** —— 前端 / 后端的平台适配（loopback 判定、
compat 行为、node 兼容开关等）：移除会让代码在真实运行环境里坏掉，**不是"少一个历史包袱"**。

> 关于 **C-05**：协议面**不转义**、界面面**转义**是**有意分面**，两侧都有注释。
> 协议面的 `SearchText` 口径见 `protocol.md` §3 / §5 —— 它**不是**协议差异（协议面就是照上游做的），
> 所以 §10 里没有这一条。**不建议统一。**
>
> 关于"双通道鉴权"与"限速系统"：**都不判为冗余** —— 前者是界面与协议面并存的必要设计，
> 后者是 F7 的加固（见 `security-fix-plan.md`）。

## 13. 上游对照：兼容性结论（基线 `28c7e596`）

### 13.1 前置

上游代码取自本地检出，与本文基线**逐字一致**（已核对）。判定只覆盖**服务端**范围内文件。
