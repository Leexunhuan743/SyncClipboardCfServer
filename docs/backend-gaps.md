## 2. 可新增（按性价比排序）

| # | 能力 | 结论 |
|---|---|---|
| 2.1 | 真推送替代 10 s 轮询 | ✅ **已实施**：`POST /ui/api/hub-ticket` 签发票据 + WebSocket 推送通道（V1 `js/signalr.js`、V2 `js/push.js`）；**轮询保留为 60 秒看门狗**，标签页进入后台即断连。实测口径：推送在线 ≈ 1 440 请求 / 天，降级轮询 ≈ 8 640 请求 / 天 |
| 2.2 | 会话可撤销（登出所有设备） | ❌ **仍未实施**。现状：登出只清本机 Cookie，已签发的令牌在有效期内仍可用；兜底通道是**改口令即让全部会话失效**。补法是在 Meta 存全局单调 `sessionEpoch`、Cookie 带 epoch、读取时比对。⚠️ **代价要如实写**：验签现在是**零 I/O**（只做 HMAC 校验），加 epoch 后**每个受守卫请求多一次 D1 读**；isolate 内存缓存只能**摊薄**（低流量下可能退化为每请求一次），且撤销是**跨 isolate 的最终一致** —— 最坏滞后 = TTL。这不是既有边界之外的小改，应**新增一条 ADR** 记录该取舍。反向教训：会话密钥曾按 isolate 缓存，导致改口令后旧会话在缓存存活期内仍被接受，该窗口被刻意消除过 —— epoch 的陈旧窗口是**功能本身**，只能收敛不能消除 |
| 2.3 | Range / 206（只给 UI 数据端点） | ✅ **已实施**：**只**给 `GET /ui/api/history/:type/:hash/data` 加（`accept-ranges`/`content-range`，不可满足 → 416）。协议侧 `/file/{name}` 与 `/api/history/{id}/data` 忽略 `Range` 是**对齐上游的有意行为**（上游 `EnableRangeProcessing` 默认 false），`test/fix-regressions.test.ts` 有断言守着，**不要顺手给协议侧加** |
| 2.4 | 数据完整性自检 | ✅ **已实施**：`GET /ui/api/integrity`，走**目录级差集**（R2 列举 × DB 期望目录集合），只对差集里的嫌疑对象逐条探测 —— **不逐条 HEAD**（1009 条逐条 HEAD 一次调用就顶穿内部服务子请求上限）。部署信息里有「数据完整性」小节 |
| 2.5 | 保留策略在线可调 | ✅ **已实施**：`PUT /ui/api/settings`（Meta 覆盖；**数字 = 覆盖、`null` = 清除覆盖回落 env、缺省 = 不改动**）。读取走唯一入口 `readRetentionSettings`，cleanup 与 `/ui/api/info` 读同一份，杜绝"清理按 Meta、界面显示按 env"的分叉。⚠️ **`0 = 关闭该阶段`** 的语义必须在 Meta 解析路径上原样保留，否则 `0` 会被当成非法值回落默认、**意外开启清理**。单独的 GET 端点因无人调用已删 |
| 2.6 | 存储 / 条数趋势 | ❌ **仍未实施**（收益有限）。若要做，三个隐含成本：① Cron 是每小时一次 ⇒ 写"每天一行"要按日期键**幂等**（多 1 次 Meta 读）；② Meta **没有任何裁剪机制** ⇒ 趋势行必须自带过期，否则键无限增长；③ 计数来源**不要**把 `statistics()` 的单条聚合拿去逐日累计，应另写按日 `GROUP BY` |
| 2.7 | 在线客户端数 / 最近同步时间 | ◑ **半做**：「最近一次变更」已显示（来自 `/ui/api/poll` 的 `lastModified`）。**在线设备数未做** —— DO 没有可读状态端点，要新增一个只读分支（注意别落到 `handleLongPoll`，空 `id` 会被当成新连接登记并挂起 25 s）；且 `/ui/api/info` 会因此变成带 DO 依赖的端，失败语义应为「DO 超时 → 该字段 `null`，其余照常」，不要整体 5xx（诊断面不能被它要诊断的对象拖垮） |
| 2.8 | 导出历史 | ❌ **仍未实施**。三条硬约束：① 全文**不能复用列表端点**（列表把正文截到 500 字符并置 `textTruncated`），逐条走单条端点是 O(N) 请求；② 若走服务端 zip，CPU 是**平均**预算（Free 档 10 ms / 调用；偶发越界由 rollover CPU time 吸收，只有**持续**越界才终止）⇒ 必须**全程流式**，不得先聚合再压缩；③ 128 MiB isolate 只在"聚合"路线下才是瓶颈。单条下载已覆盖"取回某个文件"的实际需求 |
| 2.9 | 记录级深链接 | ✅ **已实施**：`/ui_v1/#Text-<hash>` 与 `/ui_v2/app/#Text-<hash>` 打开即预览；预览时写入 hash、关闭时清除 |
| 2.10 | 服务端缩略图 | ❌ **仍未实施**，但**原因变了**：原文说的"免费档没有 Image Resizing"**是错的** —— Cloudflare Images 免费档**含** transformations，额度是每自然月 **5 000 次唯一变换**，超出后新变换报错、已缓存的不受影响。故本项从"受计划限制"变成**可做**（数据端点用 `cf.image` 或 Images binding 产出缩略图，binding 可直接吃 R2 字节）。三点注意：① binding 的响应**不会自动缓存**，要自己设缓存头（该端点现为 `private, max-age=60`）；② 用 `cf.image` + 自指 URL 时要按 `Via: image-resizing` 放行原图，否则回环；③ 额度按**唯一变换**计（同源图 + 同参数每月只算一次）。**边界**：本账号是否已启用 Images 属部署事实，仓库内无证据 |
| 2.11 | FTS5 全文检索 | ❌ **仍未实施**（低优先）。D1 支持 FTS5 模块（含 `fts5vocab`，平台文档可查）。两点注意：① **匹配语义会变** —— FTS5 是分词匹配，现在的"子串 + LIKE 元字符转义"语义（含与官方 API 的有意差异）会作废；② 存量库加虚拟表需手工 `d1 execute` 迁移（仓库目前没有 migrations 目录）。超长搜索串的**正确性不在本项**：入口已有共享的字节校验（`MAX_SEARCH_BYTES = 48`，协议与界面共用同一判定） |

## 3. 效率与规范欠账

| # | 问题 | 结论 |
|---|---|---|
| 3.1 | `statistics` 全表拉取 + 一次调用打三条查询 | ✅ **已修**：现为**一条聚合**（`SELECT COUNT(*), SUM(CASE WHEN Stared != 0 …), SUM(CASE WHEN IsDeleted != 0 …), SUM(CASE WHEN IsDeleted = 0 …) FROM HistoryRecords WHERE UserId = ?`），不再把行拉进 isolate 循环；`countByType` 的两次调用也已合并。这条很关键 —— 统计在**每次页面加载、星标、删除、切视图**都会跑 |
| 3.2 | 列表 / 统计 / info / poll 这些 JSON 响应没有 `Cache-Control` | ✅ **已修**：`/ui/api/*` 统一 `no-store`。⚠️ **例外是数据端点**：它自带 `private, max-age=60`（供缩略图 / 预览复用），按字面"一律 no-store"会把那 60 秒私有缓存打掉、预览退化成每次回源。另有两条**在路由之前就返回**的响应拿不到这个头（跨站 403 与 `UI_ENABLED=false` 的 JSON 404），都是错误响应、不含用户数据 |
| 3.3 | ~~响应压缩未确认~~ | ✅ **不是欠账**：带 `Accept-Encoding: gzip, br` 实测为 `content-encoding: gzip`，200 条列表 76 595 B → 13 733 B（−82%）。仓库内没有出站压缩代码 ⇒ 由运行时 / 边缘承担 |
| 3.4 | 变更信号是全局二元组 | ◑ **未精细化，但当前规模无感**：`readChangeMarker` 返回 `{count, lastModified}`，任何写入都让所有标签整页重拉。要精细化可带上 `type` 或版本号 |
| 3.5 | `DELETE /api/history/clear` 不广播 | ✅ **这就是最终结论（不是待办）**：上游广播触发点清单**不含 clear**，逐条广播会超单次调用的子请求上限，且给已硬删的记录推 `RemoteHistoryChanged` 载荷是伪造语义。界面与跨标签页收敛走 `/ui/api/poll` 的变更标记 |

## 4. 不做的

多租户 / 多用户、服务端会话表或内存会话、界面直连 SignalR **而不经票据签发**、Web 字体、`/dav` 前缀别名、
JSON-LD（无现实实体）、`og:image`（域名构建时未知）。

## 5. 若接着做，建议顺序

1. **§2.8 导出历史**（用户可感知的价值最高；难点在"全程流式"，不是权限）；
2. **§2.7 在线设备数**（先把 DO 只读分支的失败语义定下来，再动 `/ui/api/info`）；
3. **§2.2 会话可撤销**（要先写 ADR 把"每个受守卫请求多一次 D1 读"这件事定下来）；
4. **§2.6 趋势** 与 **§2.11 FTS5**（都需要先解决"Meta 无裁剪"与"存量库迁移"这两个共性问题）；
5. **§2.10 服务端缩略图**（取决于部署侧是否启用 Images，可能需要先做一次用量估算）；
6. **§1.4 剩下的 `id` 排序列**（要不要给 `id` 一个可见列，是个界面取舍而不是后端工作）。

## 6. 验证与证据边界

- **代码证据**：本轮重写时逐条对照**当前**代码重新判定"做没做"（`SORT_COLUMNS` 六字段、
  `statistics()` 的单条聚合、`no-store` 中间件、`integrity` / `settings` / `hub-ticket` /
  `batch-update` / `batch-purge` 端点的存在、数据端点的 `Range` 支持、`readRetentionSettings` 的唯一读入口、
  `session.ts` 里**没有** epoch）。原文的行号一律未沿用。
- **平台事实（外链，非仓库证据）**：Cloudflare Images 免费档含 transformations、每自然月 5 000 次唯一变换（§2.10）；
  Workers 免费档"内部服务"子请求上限 1 000 / 次调用（§2.4）；D1 支持 FTS5（§2.11）。三条均由当时的作者打开官方文档页核对。

## 7. 方法论（从三轮复核里留下的，值得再用）

原文记录了三轮复核（三名子代理并行只读审阅 → 顾问复核 → 实施期复核），过程留档在
`git show f6cced5:docs/backend-gaps.md`。其中**方法**仍有价值：

- **事实核对**与**可行性攻击**要分开做：前者对行号与语义，后者对"这条真做起来会撞上什么"。
  三轮共订正 10 条、判错 3 条、撤销 1 条。
- **判错的典型形态**是"看到可疑代码就下结论，没往上下游找既有的防护"：把 `LIKE '%…%'` 判成越界，
  而入口早有共享的字节校验；把 `clientCount()` 判成"只用于一行日志"，而它还有第二个调用点。
- **成本口径要落到平台的真实约束上，且要分清是"子请求数"还是"CPU"**：两者是**不同的天花板**，
  写错哪一条都会得出相反的可做性结论（§2.8 就是这么错了两轮）。
- **编号一旦被代码注释引用，就不能再重排**：本文件 §1.N/§2.N/§3.N 有 12 处代码锚点。
