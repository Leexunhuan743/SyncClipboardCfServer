> **精简介**：本节起为 2026-10-04 的整篇重写（原文 653 行）；历史版本见
> `git show <hash>:docs/frontend-checklist.md`：重写前最近一版 `48a7c33`，初版 `0c0a49d`（2026-09-17）。
>
> **这份文件是什么**：把"一个前端要想到什么"整理成可逐条检查的 24 个维度，每条写清
> **关注点 → 本仓库的判据/证据 → 落地建议**。不写"要注重用户体验"这类无法执行的话 ——
> 能用数字或文件位置表达的，都写出来。
>
> **重写时做的两件事**：① 删掉全部"某年某月某日做了什么"的过程叙述（原文里 §14/§15/§26/§27
> 大段是改动日志，与 `docs/progress.md` 重复）；② **把已经做完、已不成立的检查项从正文剔除**——
> 剩下的 24 个维度里，只有仍然需要"下次照做"的判据与取舍，没有"曾经漏过什么"。
> 每个维度的**实测数字都是当时的读数**；度量方法与其守卫至今有效，数值本身会随设计改动而变。

## 0. 先说结论

1. **本文 24 个维度不是并列的 24 件事**：其中 6 条是"地基"（用户目标、功能范围、信息架构、
   状态与反馈、组件一致性、无障碍），其余都是在地基上做取舍。地基错了，后面每一条都要返工。
2. **没有判据的维度等于没做**。"美观""流畅""完善"必须落到可复算的东西上：像素、毫秒、
   请求数、对比度、断言。本站的口径是 **量一次 → 写进文档 → 加一条守卫**。
3. **同一个事实只能有一个来源**（接口前缀、设计令牌、状态字段、文案）。V1 那次"整个界面
   不可用两天"的故障，根因就是接口前缀在两个地方各写了一遍（见 §3）。

## 1. 用户目标与使用场景

**关注点**：用户是谁、什么设备、什么频率、失败一次的代价是什么；有没有"顺手打开看一眼"的轻场景。

**本仓库的判据/证据**：**单用户自托管**服务端，两类使用者差别很大：
① 官方客户端（桌面端）——只在配置服务器地址时进入界面；② 浏览器里的"人"——查历史、复制回去、清垃圾，
多在手机上顺手看一眼。**定位是硬约定**：V1 (`/ui_v1/`) 是**产品界面 / 默认入口**（站点根与 `/ui/` 的跳转壳都指向它），
V2 (`/ui_v2/`) 只是仓库维护者的开发测试版。

**落地建议**：
- 每个界面在 README / 设计文档第一段写清"它在什么场景下被打开"以及**不负责什么**
  （反例：把"配置客户端"写进每日登录流程，用户每次都要读一遍用不到的话）。
- 场景决定首屏内容：查历史 → 列表优先；配置 → 地址与凭据优先。

## 2. 功能范围

**关注点**：做什么、不做什么、边界在哪；"已有后端能力但界面没接"的那一张清单。

**本仓库的判据/证据**：那张清单是 [`backend-gaps.md`](backend-gaps.md) §1（清理状态、置顶写入、
批量操作、排序字段、`/api/time` 展示等）。协议面端点已 100% 覆盖，界面面的缺口单独记。
V1 已接上原本缺的置顶、批量收藏/恢复、清理状态展示、5 个可点的排序列。

**落地建议**：
- 维护一份"**已建未接**"清单，并注明为什么没接（成本 / 语义 / 优先级）——
  它的价值是防止"下一轮从头再发现一遍"。
- 范围变更要同时改三处：界面、`docs/`（现状类文档）、契约测试。缺一处就会出现
  "文档说支持、点上去没有"。

## 3. 信息架构

**关注点**：命名空间、挂载点、资源归属；用户与机器分别从哪里进；哪些是契约、哪些是实现细节。

**本仓库的判据/证据**：站点切成三层，边界写在 [`ui.md`](ui.md) §2 与 `wrangler.toml`：
协议面（`/api/*`、`/SyncClipboard.json`、`/file/*`、Hub —— 官方客户端依赖，**不可动**）、
界面 API（`/ui/api/*`，V1 与 V2 共用同一套）、界面静态资源（四个挂载点 `/ui_v1/`、`/ui_v2/`、
`/ui_shared/`、`/ui/` 的跳转壳）。

**落地建议**：
- **页面挂载点与接口前缀必须分开写**，且接口前缀只允许一处字面量。证据：一次目录改名把 17 处
  接口前缀一起改成了不存在的命名空间 —— 静态资源全部 200、界面永远停在骨架屏、只报
  「初始化失败：Not Found」，却**活了两天**，因为没有任何断言碰过这个前缀。
  现在 `public/ui_v1/js/api.js` 的 `API_BASE = '/ui/api'` 是唯一定义处，
  `test/ui-guard.test.ts` 有一节断言"V1 源码里不出现那个错前缀"。
- 新增一个挂载点时先回答三个问题：谁提供（Worker / 静态资源）、开关是谁（`UI_ENABLED`）、
  缓存策略在哪张表（`public/_headers`）。三者缺一都会留下"看起来正常、行为不对"的角落。

## 4. 任务流程

**关注点**：每个任务的最短路径、需要几次交互、中途能不能退出、失败后回到哪里。

**本仓库的判据/证据**：四条主流程都有明确的终点与回退 ——
查历史（筛选 → 列表 → 预览/复制）、清理（勾选 → 批量确认 → 就地收行 → 对账刷新）、
回收站（进 → 恢复 / 清空）、维护（部署信息 → 保留策略保存 → 下一轮清理生效）。
深链接 `#Text-<hash>` 让"贴一条链接"直接落到某条记录；登录用 `?next=` 回原地址（同源白名单）。

**落地建议**：
- 每条流程写一句"成功的样子"与"失败的样子"，并让它们都能被**打开一次**看到（见 §14）。
- 有代价的操作必须说清**代价**而不是"确定吗"。两档文案分得开：
  「移动到回收站」= 所有同步设备上这条也会消失 + 30 天内**连数据文件**可恢复；
  「彻底删除」= 行与数据目录**立刻**都没了、不可撤销（`messages.js` 的
  `deleteConfirmSpec` / `purgeConfirmSpec`，两版逐字一致）。

## 5. 布局与栅格

**关注点**：内容为主角还是容器为主角；列预算怎么分；首屏"内容起点"在哪。

**本仓库的判据/证据**：数据表是 `table-layout: fixed`，列宽是**预算表**而不是自由伸缩。
V1 重做前后的实测：1440×900 下表格首行 y=357 → 298，正文列 342px → 476px。

**落地建议**：
- 给"内容列能拿到多少像素"设一条下限，改列宽时**量一次**再定（别用肉眼）。
- 固定表头 / 工具栏的吸顶高度要进 CSS 变量（`--header-h`），否则"滚动到某处"的脚本与锚点定位都会漂。
- 两个挂载点的列预算允许不同（V1 是表格、V2 是卡片），但**判据要一致**：
  "正文是主角"在两版上都要能用数字证明。

## 6. 响应式适配

**关注点**：断点为什么是这些、每个断点**牺牲**了什么、触屏命中区、横竖屏与安全区。

**本仓库的判据/证据**：断点取自有理由的取舍（V1 的 `components.css` / `layout.css`）：
完整列表 → 逐级收列 → 表格转卡片 → 工具栏换行 → 收顶栏按钮文字（都在文件末尾，带注释）
→ `@media (pointer: coarse)` 把命中区提到 44px。实测：390×844 下横向溢出 0。

**落地建议**：
- 断点写在**文件末尾**并注明"牺牲了什么"（例如 V1 的注释写着"≤560 收起顶栏按钮文字：
  390px 下品牌标题与「复制最近一条」的文字会与「部署信息」挤在一起"）。
  没有记录的取舍，下一轮会被当成 bug 改回去；**反过来也一样** —— 一条取舍被推翻时，
  要在新记录里写清"为什么当时那么换、为什么现在不换了"。
- 窄屏上"少显示一列"优于"把每列压窄"：信息仍在（卡片里有元信息行），只是换了形态。
- **不要把低频控件藏起来**：窄屏没有改页大小的地方不是取舍，是缺口 ——
  「每页条数」应与「刷新」绑成一组贴行尾，而不是 `display:none`。
- 移动端必须实测的四个量：横向溢出（`documentElement.scrollWidth - clientWidth`）、
  可点元素最小尺寸、首屏内容起点、软键盘弹出后输入框是否可见。

## 7. 信息层级

**关注点**：一屏里谁是主、谁是次；标题 / 正文 / 元信息的字号与颜色阶梯；控件主次是否与使用频率一致。

**本仓库的判据/证据**：三处层级问题都用数字说话：统计条高度（大数字压住列表）、
工具栏控件的等权问题（搜索被夹在低频控件之间）、正文列宽 vs 四个时间列的合计宽度。
对策：统计条压低、搜索放最前且可伸展、正文列拿到最大预算。

**落地建议**：
- 用"**使用频率 × 后果严重度**"排主次，而不是让控件等权：高频（搜索）给位置与宽度；
  低频（每页条数）与同为"怎么取这份列表"的刷新**绑成一组贴行尾**；不可逆操作给最重的视觉
  （红底 + 二次确认）。
- 元信息（时间 / 体积 / hash）统一降一档：`--ink-muted` + `--fs-sm`，但对比度仍 ≥4.5:1
  —— 这是"看起来轻"与"读不清"的分界线。

## 8. 色彩体系

**关注点**：语义命名而非色值命名；浅深两套是否同构；对比度是否实测；原生控件是否跟随主题。

**本仓库的判据/证据**：两版的 `tokens*.css` 都是**语义令牌**
（`--bg/--surface/--ink/--border/--accent/--danger`），浅深两套同名不同值。类型徽标四色的对比度实测全部 ≥4.5:1
（浅色 6.30 / 6.81 / 7.50 / 8.25，深色 7.55 / 7.67 / 7.36 / 7.26，按 sRGB 相对亮度算）。
`color-scheme` 按**生效主题**声明（不是跟随系统），否则浅色系统 + 应用内切深色时会混进浅色原生控件。

**落地建议**：
- 每个语义色都要有一条"用在什么底上"的记录；深色下必须**重算**对比度
  （`--danger` 上的白字在深色下会掉到 3:1 以下）。
- 强调色只留一个色相 + 一个状态色（星标琥珀），避免"彩虹徽标"。
- 用 `color-mix()` 做半透明表面时，它在深色下必须有独立取值，否则黑 6% 压在深底上等于不存在。

## 9. 字体与排版

**关注点**：字体来源与加载失败的表现；字号阶梯；数字对齐；中文标点与断行。

**本仓库的判据/证据**：**系统字体栈**而不是 Web 字体 —— 自托管 + 面向国内网络，
外部字体 CDN 大概率加载失败，会出现"先无字后有字"的闪烁（比系统栈更糟）。
全站 `font-variant-numeric: tabular-nums`：时间 / 体积 / 计数成列跳动是最廉价的"未打磨"信号。

**落地建议**：
- 字号阶梯只留 4 档并写进令牌；正文 14px、元信息 13px、标题 16–18px 是稳态。
- 长文本必须指定断行策略（`word-break` / `white-space`）：剪贴板内容可能是超长无空格串。
- 时间统一走一个格式化模块（V1 `format.js` 的 `formatRelative` / `formatAbsolute`），
  别让三处各写一份"几分钟前"。

## 10. 间距、圆角与描边

**关注点**：4px 网格；圆角分档而不是随处新值；边框与阴影各自的职责。

**本仓库的判据/证据**：`--sp-1..8`、`--r-sm/md/lg/pill`、`--shadow-pop/dialog/keyline`。
产品方言的取向是**边框优先、阴影只给浮层**（表格与行不用阴影）。
触屏命中区与桌面控件高度是**两个令牌**（`--control-h` / `--hit-min`）——
混用会让"改一处误伤另一处"。

**落地建议**：
- 新增间距 / 圆角前先问"现有档位为什么不够"；令牌数量失控比少一个档位更贵。
- 内边距的改动必须复量行高；**列的宽度下限 = 内容 + 内边距**，这类值要写进注释
  （把一列收窄到装不下两个按钮就会换行、行高反弹）。

## 11. 图标与插画风格

**关注点**：统一来源与网格；不用 emoji；装饰性与语义性图标区分；图标不能是唯一入口。

**本仓库的判据/证据**：`icons.js` 是 24×24 的常量路径表（stroke 1.7，`aria-hidden`），
经 `dom.js` 的 `svg()` 构造 —— **不提供任何插入 HTML 的途径**（剪贴板内容不可信，
一处 `innerHTML` 就是一条读取全部历史的 XSS 路径）。反例也在库里：有一处入口曾只有一枚无标签的 ⓘ，
[`ui.md`](ui.md) §9.5 记为"第一次使用者找不到"，已改成带文字的按钮（窄屏收成图标 + `aria-label`）。

**落地建议**：
- 新图标先进 `icons.js` 再使用，避免同一个含义出现两种画法。
- 图标按钮一律配 `aria-label` + `title`；**只有图标的入口**要评估可发现性
  （"看一眼就知道"的只有极少数符号：×、←、⋯）。
- 空状态可以用大号图标，但它是**装饰**，必须同时有标题与说明文字。

## 12. 组件一致性

**关注点**：一个视觉形状只有一份实现；同一状态在各组件上表现一致；避免"写好了没人用"的抽象。

**本仓库的判据/证据**：`.btn` 通过 `--btn-*` 变量派生 4 种变体；`.icon-btn` 承担纯图标动作；
`.chip / .segmented / .field / .dialog` 各自一份。`test/ui-contract.test.ts` **双向**守卫
"CSS 里定义但全站无人使用的类必须为零"（曾抓到 `.btn[aria-disabled]` 这类死规则）。
审计还抓到过两类：**抽象写好了没人用**（`setPending`/`flashOk` 零调用而 6 处手写）
与**两个所有者写同一个 DOM 子树**（对话框 `open()` 清空 body，把调用方刚 append 的说明冲掉）。

**落地建议**：
- 每个交互态（rest / hover / active / focus-visible / disabled / loading / success / error）
  在组件层定义一次，调用点只传状态。
- 一个 DOM 子树只能有一个"所有者"：`open()` 负责正文与页脚，调用方只给数据。
  这类接缝是缺陷高发区，改完要用真实页面开一次。

## 13. 交互反馈

**关注点**：反馈落在**用户按下的那个控件**上；多久给反馈；失败要不要留在原地。

**本仓库的判据/证据**：两版共用同一套 —— `setPending(button, true)` → 按钮转圈（保留宽度，避免抖动）、
`flashSuccess(button)` → 换成对勾 + 结果文案、`data-state="ok"` 自动还原；
跨控件 / 降级类信息才走 toast（最多 4 条，超出挤掉最早的）。确认对话框**不立刻关闭**：
请求期间按钮转圈、失败留在原地显示原因并可重试。

**落地建议**：
- 判据是"用户按下的是哪个按钮，结果就出现在哪个按钮上"—— "发过请求"不等于"做成了"，
  只有 `true` 才显示成功态。
- 超过 300ms 的操作必须给进行中反馈；不可逆操作失败后不要让用户重新走一遍确认。
- 批量操作是**逐条**判定的（服务端逐条走同一条写路径），失败条数要如实报出来，
  并在结束时对账刷新一次。

## 14. 页面状态设计

**关注点**：加载中 / 空 / 有数据 / 部分失败 / 失败 / 离线 / 无权限 —— 每个都要有一屏。

**本仓库的判据/证据**：V1 的状态矩阵是完整的：骨架屏（首屏）、三种空状态
（还没有记录 / 筛选中无结果 / 回收站为空）、首屏失败的错误态 + 重试、
失联横幅（`role="status"`，持续状态不用 toast）、`data-busy` 的整块降对比、登录页的错误位。
空状态带"下一步动作"（清除筛选 / 如何配置客户端）。

**落地建议**：
- 每个状态都要能**打开一次**：用查询串制造状态（用不存在的搜索词制造空结果、
  用超长搜索词制造 400 错误态），而不是等它们自然出现。
- **"文档里写了"不等于"跑起来是这样"**：骨架这类状态必须真的打开页面看见它
  （历史上骨架只存在于 `index.html` 的静态标记里，在数据到达前就被换掉，
  首屏真正的占位是空状态 —— 库里有上千条时那句话就是假的）。
- 错误文案要翻译成用户能做的动作：服务端的 `SearchText must be at most 48 bytes`
  在界面上是"搜索词过长：服务端上限 48 字节（约 16 个汉字），缩短后再试"。
- 首屏失败不能把骨架屏永远留着（"无限骨架"是最糟的一种状态）。

## 15. 边界与极端数据

**关注点**：超长文本、超大文件、0 与负数、未来 / 过去时间、重复项、超多行、并发。

**本仓库的判据/证据**：真实边界都已存在并被处理：
- 列表正文截断到 500 字符（`textTruncated` 标记，复制 / 预览前必须取单条全文，
  否则用户拿到被砍一半的内容）；截断与判定都用**码点**口径，与 SQL 侧 `length()`/`substr()` 同源。
- 大图不拉缩略图（超阈值用占位图，`loading="lazy"` 只推迟不减少）。
- `hasData=true` 但对象已丢的记录显示"数据不可用"而不是裂图
  （数据端点用 404 `data_missing` 与"记录不存在"区分）。
- 批量端点 100 条封顶，超出由前端分片。
- **未来时间戳**（客户端时钟偏快时很常见）：相对时间要分出"以后"那一档，
  否则未来的记录会退化成裸时刻（看起来像今天早上），两版都已补齐。
- 数字一律走白名单与范围校验（`pageSize ≤ 500`、`days ≤ 90`、`tz ∈ [-840, 840]`），
  前端与后端各拦一次。

**落地建议**：
- 为每类边界写出"期望呈现"并各留一条夹具；夹具的写法要能被清理任务回收
  （未来 `LastModified` 会让记录连 PATCH 都删不掉）。

## 16. 表单设计

**关注点**：标签与 `for` 绑定、自动填充、校验时机、错误的落点、提交态、危险默认值。

**本仓库的判据/证据**：登录表单有 `<label for>`、`required`、`autocomplete`、
错误区 `role="alert"`、空提交本地拦截并把焦点交回缺失字段、提交期间 `data-loading`；
保留策略表单只接受非负整数，并区分三种语义：**留空 = 回落部署环境变量**、
**0 = 关闭该阶段**、有值 = 覆盖。它刻意**不用**生效值预填输入框 ——
否则"什么都没改直接保存"会把环境变量值固化成 Meta 覆盖。服务端上限在本地校验里复写一份
（保留 0..525600 分钟、条数 0..1,000,000），越界在输入框下就地说明，不换回一个 `invalid_request`。

**落地建议**：
- 校验失败的信息要落在**出错的那个字段**旁边（`aria-invalid` + `aria-describedby` + 焦点），
  而不是统一弹一条 toast。
- "留空 / 0 / 有值"这类三态语义必须在界面上用文字说清，并显示"当前生效值 + 来源"。
- 提交按钮的标签要说结果（"保存保留策略"），不要只说"保存"。

## 17. 动效与过渡

**关注点**：动效是否对应真实事件；关掉动效后是否完全可用；时长与缓动是否成阶梯。

**本仓库的判据/证据**：`motion.css` 把动效与内容事件一一对应（新记录闪一次、行离场淡出、
成功对勾、星标弹出、浮层进出），并给出 `prefers-reduced-motion` 的**等价降级**
（不是"少动一点"，而是"不动且完整"）。准入规则只有一条：**每个动效都必须对应一个真实的内容事件，
关掉它信息不丢**。行入场只在新视图（首次 / 翻页 / 改筛选）时播；轮询刷新不做，否则整页像幻灯片。
静止页面的"跟随"那一族（相机 / 光标 / tooltip）必须**到达并停住**，静止即 `runningCount: 0`。

**落地建议**：
- 时长写成令牌（`--dur-instant` / `--dur-fast` / `--dur-standard`）并只在这几档取值；
  不自造缓动。
- 布局属性（width/height/top）参与动画时必须复量"是否引起重排"；
  表格行的位移动画会让整列错位 —— 行离场只淡出、不位移。
- 任何"靠动画事件收尾"的逻辑都要有定时器兜底（`prefers-reduced-motion` 下动画可能不派发）。

## 18. 无障碍

**关注点**：可访问名、焦点顺序与可见焦点、命中区、对比度、读屏语义、键盘可达、减弱动效。

**本仓库的判据/证据**：`:focus-visible` 全局环；`.sr-only`；`aria-label` / `aria-pressed` /
`aria-sort` / `role="status"` / `role="alert"` 按语义分配；触屏命中区 44px；
删除后焦点交接给相邻行的**同一个控件**（不是掉到 `<body>`），并在对话框关闭后的窗口内反复落点
（浏览器的补焦晚 1–2ms 到，实测会被夺走）。行间方向键 ↓/↑/Home/End 到相邻行的**同一个控件**，
Tab 顺序一个不动；探针有 `KEYNAV` 一行断言。

**落地建议**：
- 每个图标按钮都要有可访问名；**只有图标的入口**要额外评估可发现性（见 §11）。
- 键盘路径要能走完整条流程：跳到主内容 → 搜索 → 列表 → 行内动作 → 对话框。
  行数多时用方向键（纯增量），不要改 Tab 顺序去"优化"。
- 对比度、命中区、焦点可见性三者必须各有一条可复算的判据，别靠感觉。
- 明确声明**未验证**的部分（本站没跑真实读屏，全部结论由 DOM / ARIA 契约推断）。

## 19. 性能优化

**关注点**：首屏关键路径、请求数、渲染次数、载荷大小、平台预算（子请求 / 内存）。

**本仓库的判据/证据**：零构建 + 原生 ES 模块 + `modulepreload`（把两层模块瀑布压成一层）；
列表按行对账（内容没变不重建，避免轮询重载缩略图、打断动画、丢焦点）；"先比后写"；
列表正文截断 500 字符（一页 500 行 × 每条几十 KB 就是几十 MB 的 JSON）；
服务端一条聚合查询而不是把行拉进 JS。平台侧的硬约束也进设计：
单次调用 1000 次内部子请求 → 批量端点 100 条封顶；isolate 128 MiB 内存 → 请求体默认 48 MiB、
zip 解压预算随请求体收缩。

**落地建议**：
- 首屏只做"看得见的事"：列表先落地，统计 / 趋势晚一拍。
- 轮询这类周期性开销要有**降级档**：推送在线时看门狗轮询，一个开着的标签从 ≈8.6k 压到 ≈1.4k 请求/天。
- 每加一个列表 / 图表，问一句"数据变了才重画吗"（柱状图挂在 poll 的 changed 分支上，
  而不是每次轮询都拉）。

## 20. 多端与兼容

**关注点**：浏览器差异、代理与网络环境、传输降级、设备能力（剪贴板 / `ClipboardItem` / 安全上下文）。

**本仓库的判据/证据**：SignalR 三种传输逐级降级；推送通道连续失败若干次后停止重连
（避免在坏环境里白烧请求），回前台重置；剪贴板写入区分"安全上下文缺失 / 转码失败 / 被拒"
三种原因并各自给文案；`ClipboardItem` 与 `execCommand` 双路径。已知环境坑也记了：
无头浏览器不读系统代理、`wrangler dev` 新增静态文件要重启。

**落地建议**：
- 每个"现代 API"都要写清不可用时的**降级路径**（而不是只在支持时能用）。
- 代理 / 内网这类环境要有明确的失败语义：先降级（轮询），再提示，最后才停止重试。
- 兼容性结论要写清是在什么环境测的（浏览器 + 版本 + 是否有代理）。

## 21. 国际化与本地化

**关注点**：文案集中管理、`lang` 属性、日期 / 数字格式、复数与语序、RTL（如需要）、时区。

**本仓库的判据/证据**：`<html lang="zh-CN">` 正确；**两版各有一份 `messages.js`**
（V1 刻意不 import V2 的那份 —— 产品面必须自包含），两份由 `ui-guard` 的**对等守卫**钉住逐字一致；
日期由自写的 `format.js` 处理；时区处理是对的：趋势按调用方的 `tz` 切天
（`getTimezoneOffset()`），否则 UTC+8 的用户在早上 8 点前看到的"今天"其实是昨天。

**落地建议**：
- 收敛文案到一处（各版的 `messages.js`）：改一句话不该改 8 个文件。
- 时间一律"存 UTC / 毫秒、按调用方时区显示"；跨端比较时间要带时区。
- 中文没有复数变化，但把"1 条 / 2 条"这类量词写进格式化函数，将来加语言时只改一处。
- 若将来要做多语言：优先做"文案表 + `lang`"，不要先做语言切换 UI。

## 22. 状态与反馈（与 §13 / §14 的分工）

**关注点**：客户端状态的**唯一事实源**、状态之间的合法转换、并发与竞态、刷新策略。

**本仓库的判据/证据**：状态集中在 store（筛选 / 条目 / 总数 / 统计 / 选择 / 提示键 / 主题），
渲染由调用方**显式**驱动（**刻意不提供 `subscribe`** —— 全仓无人订阅的响应式接口只会误导人）；
筛选状态进 URL（可分享、可后退）；请求竞态用"最新请求胜出"（AbortController + 序号）；
每个数据源一个守卫（列表 / 统计 / 轮询互不 abort）；计数带**视图归属**，防止迟到的响应
把回收站的数写到活跃视图上。

**落地建议**：
- 状态只放一份；派生值在渲染时算。
- 每个异步结果都要能回答"它还属于当前视图吗"（序号不够时再加一个视图标记）。
- 显式的刷新点（动作后 / 轮询发现变更后 / 视图切换后）要写进注释，
  否则下一个人会加一个"看着无害"的隐式刷新，把前面所有竞态保护绕开。

## 23. 美化问题（把"好看"变成判据）

**关注点**：视觉重心、留白节奏、对齐、层级、一致性、细节（对齐 / 圆角 / 毛边）。

**本仓库的判据/证据**：把"好看"落成四类**可测的量** ——
① **重心**（首屏内容起点 y）；② **密度**（行高、统计条高度、工具栏高度）；
③ **主角**（正文列宽）；④ **一致性**（同类控件同一形状，主次与频率对齐）。
另外两条反模式被明确避开：浮动卡片式的统计、紫→靛渐变（生成式页面最典型的形状）。

**落地建议**：
- 每次"美化"都要写出这四类量里的至少一条前后对比，否则它只是一次个人偏好。
- 对齐优先于装饰：同一行的数字用 `tabular-nums`，列头与列内容的内边距一致。
- 先做减法（去掉多余的容器、边框、阴影），再做加法。

## 24. 交互逻辑与 UI 设计（收口）

**关注点**：控件语义与行为一致（按钮就是按钮）、点击目标与视觉边界一致、误操作防护、
状态可见性（用户能不能知道"现在是什么状态"）。

**本仓库的判据/证据**：工具条用 `role="group"` 而不是 `role="toolbar"`
（后者**承诺**方向键导航，而这里没实现 —— 不引入"承诺了却做不到"的语义）；
提示条**不加** `tabindex`（会自灭的元素进 Tab 顺序，焦点可能在它消失的瞬间掉到 `<body>`）；
模态期间不接管快捷键；连点同一个动作只发一次请求。滚动中的吸顶、`scroll-margin-top`、
"点空白处关闭浮层"这类细节都有对应实现或明确不做。

**落地建议**：
- 语义角色只在真的实现了对应行为时才用（`aria-sort` 要排序真的生效、
  `role="toolbar"` 要有方向键）。
- **视觉边界 = 命中区边界**，共同判据是"相邻命中区不重叠"（最小间距 ≥ 44px），
  **不是**"必须缩按钮"：可以保留小视觉尺寸、用 `::before` 把命中区撑到 44px，
  也可以直接把触屏按钮放到 44px —— 但两者都必须同时把间距拉开，
  否则 44px 命中区 + 2px 间距会重叠。
- 每个"看起来能点"的东西都要真的能点（或明确做成不可点的样式）。

## 25. 这 24 个维度怎么协同（不是并列的 24 件事）

**① 地基（1 / 2 / 3 / 22）决定其余 20 条是否要返工。**
场景与范围定不下来，信息架构就会反复；信息架构不稳，布局与响应式每改一次都要重排。
本仓库的切法是先把"协议面 / 界面 API / 界面资源"三层钉死，之后两版界面才能各做各的视觉。

**② 判据链：能算的量 → 写进文档 → 加一条守卫。**
单个维度做成"一次性对齐"很容易，难的是**持续对齐**。本站的三件套：
`test/manual/probe*.mjs` 读真实 DOM 值（行高 / 列宽 / 溢出 / 对比度 / 键盘），
`shoot.mjs` 出图给人看，`*.test.ts` 把**不变式**钉住（接口前缀、鉴权顺序、按天分桶、文案与资源数一致）。
没有第三层的维度（例如"美观"）至少要有第一、第二层，否则下一轮无法证明"改好了"。

**③ 单一事实源是跨维度的公共约束。**
接口前缀只有一处（§3）、设计令牌只有一套（§8 / §10）、状态只有一份（§22）、
文案收敛到各版的 `messages.js`（§21，且两份逐字一致）。每多一处副本，
就多一条"改了一处、漏了另一处"的路径。

**④ 反馈时序（§13）与页面状态（§14）是同一条时间轴。**
`pending → success/error` 落在按下的控件上，页面级状态（骨架 / 空 / 错 / 离线）负责整个视图。
两者混用会让用户看不懂"到底是这一条失败了、还是整页都坏了"。

**⑤ 性能预算（§19）反向约束交互设计。**
子请求上限决定了批量端点只能 100 条一笔；isolate 内存决定了请求体上限 48 MiB；
轮询成本决定了"实时推送 + 看门狗轮询"的两档设计。**先算预算，再定交互**，
否则改完界面才发现平台不答应。

**⑥ 无障碍（§18）与响应式（§6）在实现上高度重合。**
命中区、焦点顺序、可访问名、读屏语义在窄屏与触屏上同时被考核；
做完一处就要顺带看另一处，否则会出现"桌面能走通、手机上焦点掉到 body"。

**⑦ 美化（§23）是上述结论的可见结果，不是独立目标。**

## 26. `/ui/api/*` 的消费面（V1 用到哪些）

两版界面共用同一个 `/ui/api/*`（20 条路由，清单与逐条语义见 [`ui.md`](ui.md) §5）。
V1 的实际消费面：

| 端点 | V1 的用法 |
|---|---|
| `GET /overview` | **首屏合成快照**：把 `stats` / `byType` / `marker` / `info` / `serverTime` 一次带回，于是"时钟差 / 最近同步 / 清理状态"这三样排障要看的随首屏到手 |
| `GET /activity` | 统计条右侧的趋势图（按天分桶，`tz` 由客户端给） |
| `POST /history/batch-meta` | 选择条最前的「复制选中」按 100 条分片取**完整正文**（列表正文是截断的）。两条纪律：只复制文本记录（非文本跳过并如实报数）、结果按**选中顺序**重排（服务端按 D1 行序返回） |
| `GET /statistics` | 统计条与工具栏的类型计数；`byType`（随视图）与 `byTypeActive`（恒活跃）两个口径必须分开用 |
| `GET /history` | 筛选 / 排序 / 分页；`search` 上限 48 字节（约 16 个汉字），前端把 400 翻译成可执行文案 |
| `POST /history/batch-update` | ≤100 条 / 次，前端按 100 分片 —— 每条约 5 次子请求，1000 次 / 调用的上限决定了这个数字 |
| `POST /history/clear` | `scope=trash\|all`；**不逐条广播**，其它标签页靠 `poll` 收敛 |
| `GET /history/:type/:hash/data` | 整包下载 / 大图占位；已区分 `404 data_missing`（对象丢了）与"记录不存在"。**支持 `Range`（206/416）但 V1 没接** —— 除非将来做渐进式大图预览 |
| `PUT /settings` | 保留策略在线调整；上限在本地校验里给出，越界不发出去换 `invalid_request` |
| `GET /integrity` | 只在用户点"检查"时调用（要列举一遍 R2，不该每次加载都付） |
| `POST /hub-ticket` + `GET /poll` | 推送票据走会话 Cookie；`poll` 顺带回 `serverTime` |
| `GET /info` | 与 `overview` 有重叠；接了 `overview` 之后只在用户打开"部署信息"时再拉一次 |

> 反向的观察（V2 可以从 V1 学什么）写在 [`ui-v2-design.md`](ui-v2-design.md) §8.1。
> **不接的**：更强的流式上传（单文件 >64 MiB）属架构级改动，不是界面能解决的。

## 27. 仍待做（只列有判据的）

| 项 | 为什么还没做 |
|---|---|
| 列显示开关 / 多列排序（两版都没有） | 先确认这是真需求 —— 排序白名单已有 6 个字段，表头已给出 5 个可点列 |
| 大图预览护栏 | 只加在一版上会让两版不一致；且本机图片全是小夹具，写不出可复算的证据。等库里真有 >8 MiB 的图时两版一起加 |
| 行内"删除"是否给一点危险色 | 与 V2 一致地保持中性；要改应两版一起改 |
| V1 登录表单的端到端探针 | error 判据目前靠源码守卫 + 与 V2 同形（`states.mjs` 打的是 V2 登录页） |
| 写操作后只补打 `statistics`（不整只重打 `overview`） | `overview` 内部的重复计算已修；这条仍是未做的另一半 |

### 明确不做（连同理由一起记）

- 为图表引入图表库（与零构建的约束冲突；十几根柱子的实现是几十行）。
- 用 `innerHTML` 渲染剪贴板内容（XSS 面）。
- 给提示条加 `tabindex`、给工具条加 `role="toolbar"`（承诺了做不到的语义）。
- 把 `activity` / `overview` 做成"每次轮询都拉"（它们只在写入后变化）。
